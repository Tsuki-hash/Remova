## 总体结论

Remova 是一款**功能覆盖面广、安全意识突出**的 Windows 深度卸载工具：证据链评分模型、三层安全门禁、备份先行、dry-run 设计在同类开源项目中属上乘水平，后端 Rust 代码整体质量良好且配有 49 个单元测试。

但"用着不方便"的体感有明确的技术根因，核心是三类问题：

1. **主线程阻塞（P0）**：30 个 Tauri 命令中 29 个为同步命令，按官方文档，不带 `async` 的命令在主线程执行，深度分析、清理备份、安装监控快照、计划任务查询等重 IO 操作期间**整个窗口冻结**——这是"卡、无响应、点了没反应"的直接原因。
2. **核心功能缺陷（P0/P1）**：启动项"禁用"通过重命名 Run 值实现，实际**不会阻止自启动**（Windows 登录时执行 Run 键下全部值）；dry-run 结果被前端丢弃，点击"仅预览"**无任何反馈**；右键菜单注册了 `--analyze` 参数但入口不解析参数，功能半成品。
3. **前端巨石组件（P1）**：1,865 行单文件 App.tsx、40+ 个 useState、全内联样式、表格无虚拟化且 hover 触发全量重渲染，交互卡顿且极难维护。

## 2. 架构设计评审

**评分：6.0 / 10**

### 2.1 评估结论

后端按领域拆分为 19 个职责单一的模块（扫描、执行、安全、备份、还原、枚举、注册表读写、系统操作等），`lib.rs` 仅做命令注册与薄封装，边界清晰、依赖方向正确。证据链模型（score → confidence/risk → 默认勾选策略）是全项目的架构亮点。**但命令层的线程模型存在系统性错误，前端则是完全未分层的巨石结构**，两端共同构成"架构负债"。

### 2.2 优点

- **后端领域模块化**：scanner（只读扫描）/ executor（执行）/ safety（门禁）/ backup+restore（可回滚）职责正交，与"分析→预览→备份→执行→还原"的产品流程一一对应。
- **证据链模型**：`CleanupItem { score, confidence, risk, evidence[] }` 让每个待删项可解释，默认只勾选 `confirmed && risk != high`，批量模式沿用同一规则——安全策略集中且一致。
- **三层安全门禁**：扫描期 `is_safe_fs` 过滤 → 注册表项过 `safety::is_safe_to_delete_registry` → 执行期二次验证，纵深防御思路正确。
- **前后端类型对齐**：serde `rename_all = "lowercase"` 与 TS types.ts 字段一一对应，契约清晰。
- **别名式注册表路径**（HKLM64/HKLM32/HKCU 前缀）统一了 32/64 位视图的表达，可读性好。

### 2.3 问题明细

| 编号 | 优先级 | 问题 | 位置 | 说明与影响 |
|---|:---:|---|---|---|
| ARCH-1 | **P0** | **同步命令阻塞主线程** | `lib.rs:27-349` | 29/30 命令为同步 `fn`。Tauri 官方文档明确：不带 `async` 的命令在主线程执行（除非 `#[tauri::command(async)]`）。深度分析（磁盘+注册表扫描）、run_full_cleanup（系统还原点 + 全量目录备份 + 删除）、安装监控快照（遍历 Program Files 等 4 根目录，budget 8 万条目）、`schtasks /query /v`（数秒）全部执行期间 **UI 完全冻结**。批量清理时进度条只能在两个应用之间刷新。这是用户"用着不方便"的第一根因 |
| ARCH-2 | **P1** | **前端单文件巨石组件** | `src/App.tsx` | 1,865 行、40+ useState、8 个互斥面板用独立布尔量（showHistory/showRestore/showManage/showTools/showBatchSummary...）切换，无视图状态机、无路由、无状态管理。任何功能改动都在同一文件内进行，回归面不可控 |
| ARCH-3 | **P2** | **数据层无抽象** | `App.tsx` 全文 | `invoke("cmd")` 直接散落 30+ 处，无统一 API 模块、无集中错误处理、无缓存策略；后端命令签名变更时前端无编译期保护 |
| ARCH-4 | **P2** | **样式全内联** | `App.tsx:865-988` | `css` 对象定义在组件体内（每次渲染重建），`globalCss` 字符串以 `<style>` 注入；无 CSS 文件/Modules/工具链，主题色靠 JS 逐个 setProperty |
| ARCH-5 | **P3** | **错误类型缺失** | 后端全部 | 统一 `Result<T, String>`，无 thiserror 错误枚举；错误是英文裸串，靠前端 `formatError` 正则匹配 `elevate:` 前缀映射文案，脆弱 |
| ARCH-6 | **P3** | **NIH 重复造轮子** | `lib.rs:67-105`、`history.rs:68-75` | 手写 base64 编码器（有测试，质量尚可）；手写 epoch 时间戳注释自称"ISO-ish"实为纯秒数。应直接用 `base64` / `chrono` crate |

### 2.4 改进建议

1. **【立即】** 将全部重 IO 命令改为 `async fn` + `tauri::async_runtime::spawn_blocking`（照抄 `estimate_dir_size_kb` 的写法即可，估计半天工作量，体感收益最大）。涉及：`list_installed_apps`、`analyze_associations`、`run_cleanup_dry_run`、`run_full_cleanup`、`scan_orphan_leftovers`、`begin/end_install_monitor`、`list_scheduled_tasks`、`list_services`、`list_startup_items`、`restore_session_by_name`、`app_icon_data`。
2. **【阶段二】** App.tsx 拆分为：`AppList`（列表+搜索+排序）、`AnalyzePanel`（结果+勾选+证据）、`BatchPanel`、`ManagePanel`、`RestorePanel`、`MonitorPanel`、`useRemovaApi`（数据层 hook）+ 一个 `view` 状态机替代 8 个布尔量。
3. **【阶段二】** 样式抽离为 CSS 文件 + CSS 变量主题表；数据层封装统一的 `invoke` wrapper（含错误归一化）。
4. **【阶段二】** 引入 thiserror 定义错误枚举，错误序列化为 `{code, detail}` 结构供前端映射。

## 3. 代码质量评审

**评分：6.5 / 10**

### 3.1 评估结论

Rust 侧代码功底扎实：unsafe 块边界收敛、GDI/注册表句柄成对释放、目录遍历用迭代 BFS 防栈溢出、symlink 防环、`saturating_add` 防溢出，测试密度（49/4200 行）在同类项目中偏高。TypeScript 侧开启了 strict + noUnusedLocals 等严格选项。**主要扣分项：安全逻辑存在不一致双副本、若干空壳/死代码、以及一个被严格模式"逼出来"的功能 bug（dry-run 结果丢弃）。**

### 3.2 优点

- `dirsize.rs`：迭代遍历 + AtomicBool 取消 + 符号链接跳过，教科书级实现。
- `icon.rs`：ExtractIconExW 失败回退 SHGetFileInfoW，HICON/HBITMAP/HDC 释放路径完整。
- `apps.rs`：注册表枚举缓冲区按 RegQueryInfoKeyW 实际尺寸分配；InstallDate 多格式归一化有完整测试。
- `storeapps.rs`：系统包前缀黑名单 + framework/resource 包过滤 + SystemApps 路径过滤，防误删意识好。
- 前端 `iconCache`/`iconInflight` 双 Map 实现图标去重加载；`sizeCache` 缓存体积估算；`escapeHtml` 用于报告导出防注入。
- Git 提交遵循 conventional commits，信息质量高。

## 4. 功能实现评审

### 4.1 评估结论

## 8. 安全性专项评审

### 8.2 问题明细

| SEC-1 | **P1** | **驱动器根保护不完整** | `scanner.rs:237-239`、`executor.rs:122-133` | scanner 仅拦截 `s.len()==2 && ends_with(':')`（即 "C:"），**"C:\"（3 字符）不拦截**；executor 副本连此检查都没有。当前依赖 `apps.rs:188` 对 InstallLocation 去尾部斜杠间接兜底（"C:\" → "C:" 被拦截），但孤儿扫描/前端回传 items 等路径无此兜底。若构造出 path="C:\" 的 Dir 项，`remove_dir_all` 将遍历删除整盘可删文件。建议规则改为：路径为盘符根（含尾部斜杠变体）或路径组件深度 < 3 一律拒绝 |
| SEC-2 | **P2** | **CSP 为 null** | `tauri.conf.json:23` | `"csp": null` 关闭内容安全策略。当前渲染内容全部本地生成风险低，但 Tauri 官方安全审计将 CSP null 列为默认整改项；至少应设置 `default-src 'self'`（注意放行 GitHub API 更新检查） |
| SEC-3 | **P2** | **SOFTWARE 键自动删除面过宽** | `scanner.rs:497-523` + `App.tsx:795-797` | slug 精确匹配即标 Confirmed（见 CODE-4），批量清理自动执行 `HKLMxx\SOFTWARE\{slug}` 删除。应用名为通用词（Python/Git/Java/Update）时将误删共享键。建议：SOFTWARE 键降为 Suspected、批量模式排除该类、或 slug 命中多个已装应用时跳过 |
| SEC-4 | **P3** | **子进程依赖 PATH 解析** | `regops.rs:108-122` 等 | `sc`/`schtasks`/`reg`/`powershell` 按名调用，理论上存在同目录劫持面（桌面应用实际风险低；可用绝对路径 System32 加固） |
| SEC-5 | **P3** | **还原点非保证** | `executor.rs:244-247` | SRSetRestorePointW 结果被忽略（注释"non-fatal"是有意为之，可接受），但 Win11 默认常关闭系统还原且创建有频率限制——UI 从未告知用户"还原点可能未创建"，用户可能高估兜底能力；建议在清理报告中如实展示 rp_ok 状态 |

### 8.3 改进建议

1. **【立即】** SEC-1：统一 `is_safe_fs` 并补全盘符根/浅路径拒绝（`path.components().count() < 3` 拒绝）。
2. **【阶段二】** SEC-2：配置 CSP；SEC-3：SOFTWARE 键置信度降级 + 批量排除。
3. **【阶段三】** 子进程改绝对路径；还原点状态透出到清理报告。
